# ConsultBae AI Automation Assignment

## What this is
A merged database from 3 messy source systems (Naukri applicants, gig
workers, CBNexus contacts), an n8n automation that checks new submissions
against that database and emails a duplicate alert, and a mini audio
collection web app that extracts duration/sample rate/bitrate/loudness
from recordings.

## Project structure
```
consultbae-assignment/
  data/          raw CSVs + people_export.json (snapshot for n8n)
  scripts/       Task 1: normalize.py, ingest.py, export_people.py
  db/            SQLite database (generated by ingest.py, not committed)
  app/           Task 3: Flask audio submission app
  automation/    Task 2: exported n8n workflow JSON
```

## Setup

### Requirements
- Python 3.10+ (tested on 3.14)
- ffmpeg (must be on your system PATH — see note below)
- Git

### 1. Install Python dependencies
```bash
pip install flask pydub numpy audioop-lts
```
(`audioop-lts` is required only on Python 3.13+ — see Stuck Log #1 for why.)

### 2. Install ffmpeg
Download a prebuilt Windows binary from https://www.gyan.dev/ffmpeg/builds/
— specifically the **release essentials .zip** (not the git/source builds).
Extract it, then add its `bin` folder to your system PATH environment
variable. Verify with `ffmpeg -version` in a **new** terminal window.

### 3. Run the merge pipeline (Task 1)
```bash
cd scripts
python ingest.py
```
Expected output: `Loaded: 42 naukri rows, 30 gig_worker rows, 30 cbnexus
rows` / `Merged into 54 unique people`, and a database written to
`db/consultbae.db`.

### 4. Export the database snapshot for the n8n automation
```bash
python export_people.py
```
This regenerates `data/people_export.json`, which the n8n workflow
fetches over HTTP from this repo's raw GitHub URL to check new
submissions against.

### 5. Run the audio app (Task 3)
```bash
cd ../app
python app.py
```
Open http://localhost:5000 in Chrome (for microphone recording support).
Record or upload audio, submit, then view all submissions with extracted
properties at http://localhost:5000/submissions.

### 6. The n8n automation (Task 2)
The exported workflow is in `automation/duplicate-check-workflow.json`.
It can be imported into any n8n instance (Import from File). It expects:
- A webhook (POST) simulating a new applicant submission
- An HTTP Request node pointing at this repo's raw
  `data/people_export.json`
- A Code node that normalizes and compares email/phone against known
  people
- An IF node routing on `is_duplicate`
- A Gmail node sending an alert on match

## Data Issues Report (Task 4)

All issues found by direct inspection of the 3 source files, verified
against actual ingested output.

**1. No single ID is common across all 3 files.** Source 1 has
email+phone, Source 2 has email only, Source 3 has phone only. Matched
Source1↔Source2 on email and Source1↔Source3 on phone; anything left
unmatched falls back to fuzzy name+city matching and is explicitly flagged
`match_confidence = 'fuzzy'` rather than merged silently.

**2. Phone numbers are formatted inconsistently** (`9000000268`,
`+91-9000000131`, `919000000231`, `09000000287`). Normalized to the last
10 digits regardless of prefix.

**3. Emails are case-inconsistent**
(`isha.chopra95@...` vs `ISHA.CHOPRA95@...`). Lowercased and trimmed
before comparison.

**4. Same person appears twice within a single source file.** "Nikhil
Chopra" appears twice in Source 1 with two different emails but the same
phone; "R. Verma" and "Rohit Verma" appear as separate rows with identical
email/phone. Both correctly collapsed into one person since matching runs
on email/phone, not name.

**5. City names are inconsistent** (`NOIDA`/`Noida `/`noida`;
`Gurgaon`/`Gurugram` used interchangeably). Lowercased/trimmed, and
Gurgaon/Gurugram explicitly merged as the same city (official rename). We
deliberately did **not** auto-merge `Delhi`/`New Delhi`/`Delhi NCR` since
that's a bigger judgment call about scope, not just spelling.

**6. A row is shifted/malformed in source2** — `skill_tags` value landed
in the `email_id` column for one row, also duplicating a valid row
elsewhere. Detected via a missing `"@"` in the email field and skipped.

**7. A fully blank row exists in source2.** Filtered out before
processing.

**8. A repeated header row appears mid-file in source3.** Explicitly
skipped (`Name == "Name"` check).

**9. The same numeric field mixes two different units.** Source 1
`Current CTC` mixes large annual-rupee integers (`417964`) with small
decimals (`4.2`, `8.3`) that are almost certainly lakhs. Source 2 `rate`
mixes `/hr` and `k/month`. Both converted to a consistent unit — **this
conversion is a judgment call, not a certainty**, flagged as such.

**10. Boolean/status fields are encoded inconsistently.** Source 3
`Verified` mixes `Y`/`N`/`yes`/`No`/`Yes` — mapped to real booleans.
Source 2 `status` mixes casing of Active/Inactive but also includes
`paused` as a genuinely distinct third state — kept separate rather than
collapsed into Active/Inactive.

**11. Skill tags are inconsistently cased** (`REST APIs` vs
`rest apis`). Lowercased/trimmed.

**12. Applied Date uses at least 4 different formats in the same
column** — `DD-MM-YYYY`, `YYYY-MM-DD`, `D Mon YYYY`, `MM/DD/YYYY` all
appear in Source 1's `Applied Date` column, verified directly against the
raw file. The `MM/DD/YYYY` values are genuinely ambiguous against
`DD-MM-YYYY` when both day and month are ≤12. Left as a raw string rather
than guessing a parse that could silently corrupt data.

**Summary**: 12 distinct issue categories across identity resolution,
formatting, unit mixing, malformed rows, and ambiguous dates. Judgment
calls (unit conversion, city merging, fuzzy-match confidence) are flagged
explicitly rather than silently applied.

## Stuck Log

### 1. Audio app crashed immediately: `ModuleNotFoundError: No module named 'audioop'`
Python 3.13+ removed the `audioop` standard library module that `pydub`
depends on internally — this wasn't a bug in my code, the app crashed
before reaching any of my logic. Searched the exact error text, found
`audioop` was deprecated since 3.11 and removed in 3.13; I was on 3.14.
Considered downgrading my whole Python install to 3.11 to sidestep it, but
rejected that as too big a change for a one-line fix. Installed
`audioop-lts`, a community backport published specifically for this gap.

### 2. n8n's IF node routed correct data to the wrong branch
My Code node's output clearly showed `is_duplicate: true`, but the IF node
right after it kept firing the False branch. Assumed the bug was upstream
in my Code node first — it wasn't. The real cause was a type mismatch:
n8n's condition field was internally typed as Number/String while the
actual value was a boolean, so the comparison silently failed. My first
fix attempt (switching to a "Fixed" literal true/false) made it worse by
disconnecting the field from the live data entirely. Reverted that and
instead explicitly set the condition type to Boolean with the "is true"
operator, referencing the field directly.

### 3. ffmpeg wasn't recognized after "installing" it
My first download from gyan.dev turned out to be ffmpeg's **source code**
(files like `configure`, `libavcodec`), not a compiled Windows binary — no
`.exe` existed to even point to. Re-checked the download page and found
several similarly-named options (git vs release builds, full vs
essentials); grabbed the correct "release essentials .zip" the second
time. Extracted it, added the `bin` folder to my Windows PATH, and
restarted my terminal (required — PATH changes don't apply to already-open
terminals).

## Task 5 — Scaling to 5,000 workers (stretch)
See `TASK5_SCALING.md` for the full write-up. Short version: the current
Flask dev server and SQLite database are the first two things that would
break under real concurrent load — both are explicitly flagged as
non-production by their own tooling. Before a real launch I'd move to a
proper WSGI server + Postgres, move audio storage off local disk to object
storage, process audio extraction asynchronously, and add upload size/rate
limits that don't currently exist.
